# Scale envelope results, 2026-11-27

Measured 2026-11-27 against release 2026.4 (the published tree, copied
unchanged). Script: `benchmarks/scale.py`. Raw numbers:
`benchmarks/scale-results.json`. Library code was not modified.

## Machine caveat, read this first

These numbers come from a shared, throttled VM (1.5 shared CPUs,
Python 3.12.3). The CPU is periodically starved by the host, which is
visible in the data as rare single-call latency spikes (one call in
the throughput run took 146 ms while the p95 was 0.437 ms). Treat
every figure here as a floor for real hardware, not a ceiling: a
dedicated machine will do better, and nothing here is a promise about
a customer's machine.

## Method

Both measurements use the configuration a real deployment runs: a
`Gate` from `soul_cradle.plug` with a sealed ledger attached, so every
check pays the full panel judgment, the SHA-256 hash, and the ledger
append. The evidence packet is the standard favorable packet from
`benchmarks/latency.py`, with the action description varied per call.

Throughput: after a 200-call warmup, sealed `Gate.check` calls ran
back to back in a single process for a fixed 30 second window.
Per-call latencies were recorded with `time.perf_counter()`.

Ledger growth: one ledger was grown in a single pass through 10,000,
100,000, and 1,000,000 entries. At each size the clock read total
append time since the first entry, then `verify_ledger()` recomputed
the full hash chain and was timed separately. Verification returned
True at every size.

## Throughput results

| Metric | Value |
| --- | --- |
| Window | 30.0 s |
| Checks completed | 93,621 |
| Checks per second | 3,120.7 |
| Mean latency | 0.320 ms |
| Median latency | 0.294 ms |
| p95 latency | 0.437 ms |
| Max latency (single throttled call) | 146.079 ms |

For comparison, the single-check sealed latency measured 2026-11-26
was a mean of 0.292 ms. The sustained run's median of 0.294 ms sits
right on it, so the gate does not degrade under back to back load in
one process: throughput is the single-check cost, repeated.

## Ledger growth results

| Entries | File size | Total append time | Append per entry | Full-chain verify time | Verify per entry |
| --- | --- | --- | --- | --- | --- |
| 10,000 | 39.5 MB | 3.21 s | 0.321 ms | 0.75 s | 0.075 ms |
| 100,000 | 394.8 MB | 32.70 s | 0.327 ms | 7.57 s | 0.076 ms |
| 1,000,000 | 3.95 GB | 324.79 s | 0.325 ms | 69.93 s | 0.070 ms |

Each sealed entry is about 3.9 KB on disk, because the entry carries
the full evidence packet and the full panel result.

## What the numbers say

Append cost is flat. Per-entry append time is 0.321 to 0.327 ms
across three orders of magnitude, because each append is one hash and
one line written, independent of chain length. Appending does not get
slower as the ledger grows.

Verification is linear, as a hash chain must be: it re-reads and
re-hashes every entry, so verify time grows in direct proportion to
entry count (0.75 s, 7.57 s, 69.93 s). At one million entries a full
verification takes about 70 seconds on this throttled VM. That is the
honest price of the tamper-evidence guarantee, and it is paid only
when someone asks for a full audit, not per judgment.

Storage is the real envelope limit, not speed. A million judgments is
about 3.95 GB of ledger. Any deployment sealing every judgment should
plan rotation or archival on size, not on performance.

## Incident note, for the record

A first run of this benchmark put its scratch ledger in the system
temp directory, which on this VM is a 512 MB tmpfs. The disk filled
at roughly 65,000 growth entries and the run died with a
no-space-left error. The throughput figures and the 10,000-entry row
from that run were completed before the failure, but nothing from the
corrupted run is reported here. The benchmark was rerun end to end
with scratch space on the workspace disk, and every number in this
document comes from that clean rerun. The script now creates its
scratch directory beside the repo and says why, so the mistake does
not repeat.
